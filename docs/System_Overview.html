1. What the system does

A hospital produces a constant stream of events: admissions, discharges, transfers, ICU moves and surgeries. This system ingests that stream, keeps it as an immutable record, and turns it into answers an administrator can act on: how many patients arrive (by department, hour and source), how full the beds are (counts, free beds, hours above 90%) and which days or hours were unusually busy or quiet compared with what is normal for that weekday and time. The data is simulated (1,000,000 events across eight departments over 2023–2025); no real patient information is used.

2. End-to-end flow

  1. Ingest. A source sends one event (POST /events) or registers a bulk file in object storage. An API key identifies the source; every event is validated, then appended to the raw store. Raw rows can never be updated or deleted (a database trigger enforces it).
  2. Analyse. An analyst starts a job for a date range. The system splits it into partitions of one day and one department (8,768 for the full dataset) and queues one small task per partition.
  3. Map. Workers run the tasks in parallel. Each task reads only its own slice and produces partial totals (admissions, stay lengths, hourly bed counts). Tasks share nothing, so more workers means faster jobs.
  4. Shuffle and reduce. Partial totals are grouped through Redis. Reducers merge them, run the unusual-workload detector, and write the final rows to the analytics tables in one bulk, repeat-safe step. Each row records which job produced it.
  5. Serve. The web interface and API read the precomputed tables, so a page loads in milliseconds however many raw events exist.

3. How the main parts work

PartApproach
Unusual workloadsEach department has its own baseline per weekday/weekend and hour (admissions) or day of week (bed use), built from the previous 35 days. A period is flagged when it sits far above or below that baseline. Already-flagged values are left out of the baseline so a surge does not teach the detector that surges are normal. Severity: moderate, high, critical. On the injected test incidents it found 7 of 7.
SecurityPasswords hashed with bcrypt; short-lived JWT access tokens with rotating refresh tokens (a replayed token revokes the session); API keys stored only as hashes; three roles (viewer reads, analyst also runs analyses, admin also manages keys); per-client rate limiting.
ObservabilityStructured JSON logs with a correlation id across API and workers; job progress per partition; metrics for processing time, latency and errors.
Web interfacePlain HTML/CSS/JavaScript, no build step, served by the API. Five pages (Overview, Admission patterns, Resource utilisation, Unusual workloads, Reports); running analyses and connecting data sources sit under Settings because they are set-up tasks, not daily ones.
DeploymentDocker Compose: API, workers, PostgreSQL 16, Redis, object store, behind a Caddy proxy that provides HTTPS. One script sets up a fresh server.

4. Why it is built this way

DecisionReason
Immutable raw store, derived tablesHospital records must be auditable. Analytics can be recomputed from the raw record at any time, and each result traces to the job that made it.
Partition by day × departmentAdmissions and bed counts add up cleanly across days and departments, so the work splits into independent pieces with no coordination between them.
Map/reduce on Celery workersShows the data-intensive pattern directly: independent map tasks, a shuffle, a reduce. At this scale (1M events) it runs on one machine; the same design adds workers or machines to go further.
Precompute, then serveReading finished tables keeps latency flat as data grows (measured below), and the heavy work never competes with page loads.
Repeat-safe writesA re-run or a redelivered task overwrites the same rows instead of duplicating them, which makes retries and crash recovery safe.
PostgreSQL + RedisPostgres gives transactions, monthly partitions and upserts for the record of truth; Redis is fast, short-lived working state that can always be rebuilt.

5. When things fail

  • A worker dies mid-job. Tasks are only acknowledged when finished, so the broker hands a dead worker's tasks to the survivors after 45 seconds. Tested by killing a worker at 40% of a 1M-event job: the job still finished and the results were identical (checksum-matched) to a run with no failure; recovery took about 46 s.
  • Database briefly unavailable. Tasks retry with growing waits; a long outage ends the job as “partial” and names the failed partitions. The API answers 503 instead of hanging.
  • Redis (the queue) unavailable. New analyses are refused with a clear message, but event ingestion keeps working because it never touches the queue.

7. Trying the demo (about three minutes)

  1. Open the demo link and sign in with the viewer login above (read-only).
  2. Overview: key figures against the previous period; use the period buttons and department filter, which stay selected as you move between pages.
  3. Resource utilisation: beds in use and free per department, hours above 90% compared with the previous period, and a day-by-hour heatmap.
  4. Unusual workloads: click any row to see why it was flagged. Reports: print the one-page summary, download CSVs, and see the measured results above.
  5. With the admin login: Settings → Analyses to start a new analysis and watch partitions complete live; Settings → Integrations to create an API key and send an event.

Limits. Single server and single database (not highly available); simulated data; the benchmark figures come from one machine, so absolute speeds are indicative while the scaling shape and the failure behaviour are the evidence.
